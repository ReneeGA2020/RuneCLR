# Official upstream regressions and Windows R2R comparison

On 2026-10-12, four unchanged upstream CoreCLR test projects passed their
official generated standalone runners on the private Windows x64 Checked
baseline. Each project ran with JIT and interpreter mode 1, first with default
interface dispatch and then requesting cached interface dispatch: **16/16
official project executions passed**. Separate two-Tick and three-Tick
native-R2R/IL-host matrices each passed **4/4** groups, twenty collectible
sessions per group. These
are desktop regression controls for the [iOS R2R investigation](ios-r2r-investigation.md).
They do not resolve the iOS failure.

## Official test coverage

| Upstream project under `src/tests/Loader/CollectibleAssemblies` | Relevant coverage | Interpreter successful dumps per run |
| --- | --- | ---: |
| `GenericVirtualMethod/GenericVirtualMethod.csproj` | Ten load/invoke/unload cycles, expected generic virtual exception, managed virtual-function-pointer-cache flush sentinel | 50 |
| `Statics/CollectibleStatics.csproj` | Shared-interface calls to collectible instance accessing ordinary, thread-local and object statics | 8 |
| `ResolvedFromDifferentContext/ResolvedFromDifferentContext.csproj` | Four shared-interface dependency scenarios, collectible cross-context lifetime and rejection of collectible dependencies in non-collectible parents | 1 |
| `ByRefLocals/ByRefLocals.csproj` | Collectible types remain alive through ByRef locals, then retire after the owning stack returns | 1 |

For every execution, the upstream `.cmd` invokes the private `corerun.exe`,
expects managed exit 100, observes actual exit 100 and prints
`END EXECUTION - PASSED`. The wrapper itself exits zero. Interpreter runs also
require successful targeted `Compiled method:` output; a passing wrapper exit
by itself does not establish that a conditionally skipped test executed.

The runner and assertions are the upstream projects and generator, not the
earlier simulator source-test adapter. These related tests cover collectible
state and dispatch lifetime, but none is an exact regression for the iOS
native cached-dispatch failure.

## Windows repeated-Tick controls

The independent fixture starts from the shared `IProbe`/`Tick(int, TimeSpan)`
contract and IL plugin in [the reduction builder](../eng/ios-r2r-repro.py).
Its no-inline trusted `Driver.CallSite` calls `Start`, runs a two-iteration
loop containing one interface `Tick` call site, then calls `Stop`. Each tick
has before/after markers. This deliberately exercises a second invocation
from the same call site before the first context retires; the prior one-Tick
fixture did not exercise within-session repeated calls. Two invocations do
not guarantee a cache hit: the original prestub can suppress insertion on
the first resolver entry, and the second callback can publish the cache entry.
A third callback is needed to exercise that entry. See the
[source-level cache analysis](ios-r2r-cache-analysis.md).

The later three-Tick control uses the exact shared contract, plugin and host
source generated by `reduction_sources(SOURCES)` in
[the new minimal reduction](../eng/ios-r2r-minimal.py). Its no-inline
`CallSite(IProbe, int ticks)` loops at the same interface call site and records
`TICK_BEFORE` / `TICK_AFTER` around all three callbacks before requesting
unload. It runs twenty sessions for each host/dispatch combination in a new
evidence directory. The original two-Tick input and evidence are preserved.

| Host layout | Requested `UseCachedInterfaceDispatch` | Two-Tick result | Three-Tick result |
| --- | ---: | --- | --- |
| Native R2R host | 0 | 20/20, both callbacks returned and all contexts collected | 20/20, all three callbacks returned and all contexts collected |
| Native R2R host | 1 | 20/20, both callbacks returned and all contexts collected | 20/20, all three callbacks returned and all contexts collected |
| Original IL host | 0 | 20/20, both callbacks returned and all contexts collected | 20/20, all three callbacks returned and all contexts collected |
| Original IL host | 1 | 20/20, both callbacks returned and all contexts collected | 20/20, all three callbacks returned and all contexts collected |

All groups use `InterpMode=1`, `ReadyToRun=1`, tiering disabled, and an IL-only
plugin outside the trusted composite. Each group contains twenty successful
`Plugin:Tick` interpreter dumps. The two-Tick groups have twenty second-tick
markers `PLUGIN_TICK counter=2 index=1 ticks=160000`. Every three-Tick group
has twenty third-tick markers `PLUGIN_TICK counter=3 index=2 ticks=160000`,
twenty before/after/plugin markers for each of its three tick indices, and
twenty completed collections. Plugin statics reset per session. Each host
variant loads a fresh process for each dispatch setting.

The three-Tick host source SHA-256 is
`dc5f349177af994af70c8a57bfbba0ea0069201b1e81bda38af2a33309939990`.
All four source identities, original input DLLs, composite layout and compiler
arguments are recorded independently in its per-variant `identity.json`.

The source crossgen2 creates trusted contract/entry/host composite components
for the R2R variant; the IL control excludes the host and copies its original
IL unchanged. Host PE metadata records a nonzero managed native header only
in the R2R variant. The native host `Driver.CallSite` has neither interpreter
compilation nor reported JIT compilation; the IL control has one successful
CallSite interpreter dump per process. Both variants use byte-identical
original plugin IL, whose native header is absent.

The Windows build contains `FEATURE_CACHED_INTERFACE_DISPATCH` and
`FEATURE_DYNAMIC_CODE_COMPILED`. Its default cached-dispatch setting is zero;
the source defaults to one when dynamic native compilation is absent, as in
the iOS lane. The matrix explicitly records requests for both settings.
Windows x64 execution and its entrypoint/ABI configuration do not establish
the behavior of the ARM64 iOS simulator runtime. Neither the two-Tick nor
three-Tick Windows input reproduces the crash.

## Reproduction

Read the selected runtime checkout instructions:
`docs/workflow/testing/coreclr/testing.md`,
`docs/workflow/testing/coreclr/windows-test-instructions.md`, and
`docs/workflow/building/coreclr/README.md`. They require matching CoreCLR and
managed library build outputs. If no Core_Root exists, the documented
preparation is `src/tests/build.cmd checked generatelayoutonly`, after those
prerequisites. This experiment reused the existing verified Core_Root.

The official individual build path is `dotnet.cmd build -c Checked <project>`.
`BuildAsStandalone=true` selects the official standalone wrapper; priority 1
is enabled for `ResolvedFromDifferentContext`. The driver first restores the
upstream `Common/test_dependencies` project to the same private output root,
then builds the four projects and runs their generated `.cmd` files with
`CORE_ROOT` set.

```powershell
./eng/verify-cid-upstream.ps1 -RuntimeRepo E:/runtime
./eng/verify-cid-upstream.ps1 -RuntimeRepo E:/runtime -CachedDispatch 1
```

`-EvidenceDirectory` must identify a new directory. `-CoreRoot` can select a
different prepared matching Checked layout. Each invocation runs the four
projects in both JIT and interpreter modes.

For the Windows native probe, provide a prepared source directory containing
`ProbeContract.cs`, `ProbePlugin.cs`, `ProbeHost.cs`, and `ProbeEntry.cs` with
the two-Tick fixture above. The measured source snapshot is preserved under
`artifacts/cid-windows-twotick-sources-20261012` and is also copied into the
final evidence. The three-Tick snapshot is
`artifacts/cid-windows-threetick-sources-20261012`, matching the new iOS minimal
reduction. `-ProbeTicks` defaults to two and selects the number of callbacks;
the driver requires all corresponding before/after/plugin markers to appear
twenty times, plus twenty completed collections.

```powershell
./eng/verify-cid-upstream.ps1 -RuntimeRepo E:/runtime -ProbeOnly `
  -ProbeSourceDirectory E:/RuneCLR/artifacts/cid-windows-twotick-sources-20261012
./eng/verify-cid-upstream.ps1 -RuntimeRepo E:/runtime -ProbeOnly -ProbeTicks 3 `
  -ProbeSourceDirectory E:/RuneCLR/artifacts/cid-windows-threetick-sources-20261012
```

Omit `-ProbeOnly` to run official tests and the probe together. Compiler/native
DLL reference filtering, PE layouts, original IL hashes, source snapshots,
crossgen arguments and source compiler identity are recorded in each probe
lane. Test settings are restored before invoking the SDK/compiler and after
the run so interpreter diagnostics do not affect build processes.

## Evidence and preserved attempts

- `artifacts/cid-upstream-official-verified-20261012`: 8/8 official project
  executions with default dispatch; original generated wrappers and logs.
- `artifacts/cid-upstream-cached-dispatch-20261012`: 8/8 official project
  executions requesting cached dispatch, plus the final 4/4 Windows probe
  matrix. `request.json`, `results.json`, `driver.ps1`, probe `identity.json`,
  sources, PE files and full interpreter logs retain the measured inputs.
- `artifacts/cid-windows-threetick-20261012`: subsequent 4/4 three-Tick
  controls, using the exact new minimal reduction sources. Every original
  two-Tick evidence file remains unchanged; the three-Tick directory stores
  its own driver/source snapshots, hashes, request, results and full logs.
- `artifacts/cid-upstream-20261012`: first build missing isolated
  `test_dependencies` assets (`NETSDK1004`), followed by the successful
  restored manual generic-virtual JIT/interpreter executions.
- `artifacts/cid-upstream-official-20261012`: guard-rejected first scripted
  attempt; PowerShell null-to-empty environment conversion made the upstream
  GC-stress detector skip the test even though the wrapper exited 100.
  Explicit `GCStress=0` and true null-string clearing fix the input.
- Earlier `cid-windows-twotick*` directories preserve compiler preparation
  failures involving a native DLL reference and a scalar PowerShell argument
  splat. Neither failure reached managed probe execution.

The dedicated interpreter-wide `JIT/interpreter/InterpreterTester` project
was inspected but not run: its native `pinvoke` test dependency was not built
in the available layout. It launches a separate interpreter-selected process
and needs the documented native-test build prerequisites. This targeted
result is not a claim that the complete upstream interpreter suite passes.

The remaining runtime work is an exact iOS cached-dispatch regression for
the actual failing configuration, followed by the official
upstream runner on the corresponding patched runtime. Physical-device
acceptance remains separate.
